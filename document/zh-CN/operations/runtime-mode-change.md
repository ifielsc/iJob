# 运行模式变更与回退

[English](../../en/operations/runtime-mode-change.md) · [手册首页](../README.md)

## 变更前

记录当前模式、数据库产品/位置、程序哈希、节点职责、路由、账号来源和一致性配置，完成可恢复备份。SQLite → 服务数据库是数据迁移，不是只改 JDBC 地址；当前没有跨产品一键迁移流程。先在独立目标验证迁移和恢复。

## STANDALONE → CLUSTER

1. 暂停新触发，处理在途实例，停止所有旧实例。禁止两种模式同时连接同一个业务库。
2. 确认目标共享库、账号权限、程序兼容和安全配置一致。每个节点创建独立 home/名字/目录。
3. 设置 CLUSTER 与计划角色/分组，保留迁移和必要维护机制；不要为绕过错误关闭保护。
4. 先启动 A，确认 READY、数据库和角色状态；再启动 B，检查兼容性、在线与领取行为。
5. 运行无外部副作用的单任务/作业/调度样例，核验执行节点、日志与故障恢复，再恢复业务。

## CLUSTER → STANDALONE

停止新业务并停止所有节点后，确认数据库兼容、在途工作与协调状态可按受支持路径恢复，再启动唯一 STANDALONE 实例。若启动保护拒绝，保留证据并分析，不能清协调记录强制切换。

## 回退条件

失败时先停止新节点，防止旧/新模式混跑。只有程序/数据库兼容、原配置匹配且副作用已核对时才能恢复旧部署；否则在新目标恢复匹配备份。已有集群改密钥/认证指纹、跨数据库迁移或不同协议混跑不属于本流程的自动能力。
