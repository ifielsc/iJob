# 工作区与环境存放规范

维护工作区采用以下固定布局，实际绝对路径只写在本机外层入口，不进入仓库：

```text
<workspace>/
  AGENTS.md / README.md
  iJob-repo/                       # 唯一维护的 Git 源码
  tooling/                        # 本机工具，不保存运行数据
  runtime/<env-id>/
    README.md                     # 用途、负责人、状态、启停入口
    resources.md                  # 人可读资源登记
    environment.yaml              # 机器可读非秘密清单
    config/                       # 本环境实际配置及工具路径
    secrets/                      # 受限凭据文件，不入库
    data/                         # 本环境独立持久数据
    runs/<run-id>/reports/         # 本轮日志、JUnit、哈希与结论
    runs/<run-id>/temp/            # 本轮独立 fixture 和临时数据
  maintenance/references/          # 历史规范副本及来源哈希
  maintenance/migration-records/   # 迁移清单、恢复资料与核验记录
  archives/legacy-db/<commit>/     # 冻结历史 SQL 和清单
```

新环境按需新增 `runtime/<env-id>`；先复制本规范的结构并登记资源，再创建服务。每套环境的新数据库、账号、数据目录、SFTP 身份与目录、密钥、端口、队列、bucket、容器项目/volume 均需独立。远端服务也在该目录登记，目录不是要求所有资源都必须运行在本机。可共享只读 JDK/Node/PostgreSQL 二进制及依赖缓存；共享二进制不等于连接已安装的数据库服务。

`resources.md` 和 `environment.yaml` 至少记录：环境 ID/用途/状态、负责人、源码提交与版本、OS/架构、资源类型/版本、创建方式、实例身份、地址端口、库/schema/账号名、数据根目录、秘密文件引用、SFTP 主机指纹与远端目录、网络和权限、启停/备份/恢复步骤、生命周期及清理归属。动态 fixture 记录分配规则，并在本轮报告补记实际身份。未使用的外部资源写“未创建”，不以占位配置伪装已部署。

应用配置放 `config/`，秘密放 `secrets/`；清单先写非秘密配置约定，确定后同步此规范与模板。日志、数据库和资源目录始终归属环境，不落入当前源码目录；CI 临时 runner 可沿用仓库忽略的报告路径上传产物，本地运行使用显式 `-ReportRoot` 和 `-TemporaryRoot`。每轮目录必须全新，保留失败记录，不覆盖旧证据。

隔离验证入口先拒绝继承业务配置和占用端口，不停止现有服务。后端、专项和 Full 分开执行，Full 七套配置串行。运行结束应核验仅本轮服务已停止，并把结果和实际资源写回清单。

旧环境和旧数据本轮保持原样。只有新环境独立验证、依赖盘点及恢复资料齐备后，旧目录才适合归档迁走；归档是历史追溯和回退资料，不承诺永不使用。迁走前核对外部脚本、服务配置、计划任务、IDE 与目录链接的旧路径引用，并保留归档索引、校验和和恢复方法。删除或卸载另行处理，不因迁移成功自动执行。
